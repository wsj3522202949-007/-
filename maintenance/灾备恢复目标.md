# 灾备恢复目标（RTO / RPO）

> 依据：**NIST SP 800-34** 指出，灾备不是"有备份脚本"，而是**定期测试、恢复演练、
> 记录恢复目标（RTO/RPO）并持续维护**的完整过程。本文档定义知识库的恢复目标，
> 作为季度演练的验收基准。

## 一、恢复目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| **RPO**（恢复点目标） | ≤ 24 小时 | 每日 23:30 自动备份推送，最多丢失 1 天的改动 |
| **RTO**（恢复时间目标） | ≤ 30 分钟 | 从 GitHub 完整克隆 + 门禁校验，实测约 1-3 分钟 |
| 恢复源 | GitHub origin/main | 唯一权威远端（git@github.com:wsj3522202949-007/-.git）|
| 恢复验证 | 门禁 run_all.py | 克隆后必须跑通统一门禁才算恢复成功 |

## 二、恢复分级与优先级（NIST 恢复顺序）

| 优先级 | 数据 | 恢复方式 |
|---|---|---|
| P0 | projects/（小说正文+账本） | git clone → 门禁校验（季度演练覆盖） |
| P1 | tools/scripts/（门禁与工具） | git clone 即完整（与 P0 同仓库） |
| P2 | 维护状态（maintenance/state/） | 不入库，可重建（备份日志/状态文件） |
| P3 | 参考文献快照（references/原始来源包） | 外部来源可重新抓取 |

> 说明：maintenance/state/ 与 references/原始来源包 在 .gitignore 排除区内，
> 不参与 git 恢复。若本机丢失，P2/P3 按"可重建"处理，不计入 RTO 验收。

## 三、验证方式（季度恢复演练）

由 `maintenance/scripts/quarterly-recovery.ps1` 自动执行，每季度（3/6/9/12 月）1 次：

1. 创建临时目录 → `git clone` 真实拉取远端
2. 在克隆副本上运行 `run_all.py` 统一门禁
3. 生成恢复演练报告（`maintenance/reports/recovery-drill-*.md`）
4. 记录克隆耗时/门禁耗时/结果到 backup-log.jsonl 与季度状态文件

**验收标准**：克隆成功 + 门禁 0 ERROR → 演练通过（RTO 实测 ≤ 30 分钟）。

## 四、持续维护要求（NIST "保持计划最新"）

- 每日备份（KnowledgeBase_DailyBackup 23:30）：gate → commit → push → 远端 HEAD 校验
- 每季度演练（KnowledgeBase_QuarterlyRecovery）：验证克隆+门禁可恢复性
- 每次修改灾备脚本或远端地址后，**必须**手动触发一次演练验证
- 演练失败必须留下 failed 记录（不得静默跳过），下次季度自动重试

## 五、相关文件

- 演练脚本：`maintenance/scripts/quarterly-recovery.ps1`
- 每日备份：`maintenance/scripts/daily-backup.ps1`
- 演练报告：`maintenance/reports/recovery-drill-*.md`
- 运行日志：`maintenance/state/backup-log.jsonl`
